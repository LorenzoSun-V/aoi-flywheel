# 在真机上测 worker 出故障时任务会怎样

GPU worker 被杀掉、死机、断网时任务怎么收场，自动测试里是用一两秒的租约和假的命令测的（`tests/server/test_jobs.py`、`test_evals.py`、`test_predictions.py`），**在真的 GPU 机、真的网线、真的 TensorRT 推理上还没有验证过**。这份文档是一套照着做的步骤，做一遍大约一个小时。每一步写了怎么做、应该看到什么、怎么核对；和「应该看到」不一样的地方就是要修的问题，把那一步的输出和 `fw job show` 的结果发回来。

## 先知道这几条规则

测的就是这几条在真机上成不成立：

1. worker 领到任务时拿到一个租约，默认 60 秒（服务器的 `FW_JOB_LEASE_SECONDS`），每 20 秒续一次，每次续成「这一刻起 60 秒」。所以 worker 突然没了以后，租约在 **40 到 60 秒**后到期（看它离上一次续租过了多久）。下面说的「租约到期」都是这个范围；你每 20 秒看一次的话，会在 40 到 80 秒之间看到状态变化，45 秒就变了是正常的。
2. 租约到期没续上，平台把任务放回队列，等下一次领取。同一个任务领取 3 次都失联，就算失败。
3. 平台每隔一会儿（租约的四分之一，最长 15 秒）查一次租约，收回过期的；有人看任务（`fw job list`、`fw job show`、网页的任务页）或者有 worker 来领任务时也会顺便收回。所以即使只有一台 worker 而且它整台机器没了、也没有人看，任务也会在租约到期后十几秒内回到「排队」（或者记成失败、已取消）。（2026-11-14 之前平台不会主动查，没人看就一直显示「运行中」。）
4. 失联的 worker 回来以后，它手里的旧令牌作废：它交的结果平台不收，它自己也会停下正在跑的命令。同一个任务不会在两处同时算数。
5. worker 自己报告的失败（命令出错）不重试；只有失联才重新排队。
6. 取消一个运行中的任务：worker 在下一次续租（最多 20 秒后）时知道，杀掉正在跑的命令，任务变成「已取消」。

## 准备

- 一台平台服务器，一台 GPU 机（下面叫 gpu-01），最好再有第二台 GPU 机或者同一台机器上的第二个 worker 账号（第 5 步用，没有可以跳过）。
- GPU 机上 worker 用 systemd 常驻（`docs/commands.md` 的「fw worker」一节），推理环境已经登记，`fw runner check <环境名>` 能通过。
- 一个**跑得够久**的任务：对一个几千张图的目录做评估或推理，要能跑 5 分钟以上，这样才来得及在中途动手。下面写成：

  ```
  fw eval run <模型>@<版本> --data <数据集>@<版本> --dirs <一个大目录> --runner <环境名>
  ```

  `fw eval run` 每次都排一个新任务，所以每一步重复这一条就行。（`fw predict run` 不一样：同样的请求会复用已有的任务，用它来测的话每一步要换一个目录。）
- 开三个终端：
  - A（你自己的电脑，algo 账号）：提交任务，`fw job show <编号>`、`fw job log <编号> -f`。
  - B（GPU 机）：`journalctl -u fw-worker -f` 看 worker 的输出。
  - C（GPU 机）：`watch -n 1 nvidia-smi` 看 GPU 上有没有进程。
- **确认这台 GPU 机上没有别人在跑的训练或别的程序**：第 4 步会强制重启整台机器，第 5 步会断它的网。
- 记下开始前的状态：`fw job list` 里没有排队和运行中的任务；`nvidia-smi` 里没有推理进程。

每一步做完都用这四样核对，下面简称「核对四样」：

1. `fw job show <编号>`：状态、每一次领取是哪台机器、怎么结束的。
2. 终端 B 里 worker 说了什么。
3. 终端 C 里 GPU 上还有没有上一次的推理进程。
4. GPU 机上任务的工作目录（默认 `~/.cache/fw/jobs/`，或者 `FW_WORK_DIR`）里有没有留下上一次的子目录（名字是 `job-<任务编号>-<第几次领取>`）。

## 平台和 worker 在同一台机器上时

平台服务器自己带 GPU、worker 就跑在它上面（worker 登录时写的是 `http://127.0.0.1:8000`）也能测，终端 A 用另一台电脑（比如笔记本），终端 B、C 用 SSH 连到服务器。有三步要换做法，其余照做：

| 步骤 | 这种情况下 |
|---|---|
| 1、2、3、6、7、8 | 照做 |
| 4 断电 | 能做，但平台也一起断，测的是「整台机器重启后都能自己回来」，预期见下 |
| 5 拔网线 | **不能照做**：worker 连的是本机地址，拔网线、关网卡都断不开它，只会断掉你的 SSH。改用下面的办法 |
| 5b 里「被第二台 worker 领走」 | 看不到（只有一台 worker）。只看任务回到「排队」、恢复后同一台 worker 第 2 次领取并完成 |

**第 5 步的断网，改成只拦 worker 这个账号到平台端口的连接。** SSH 和别的电脑到平台的访问都不受影响，所以断的期间可以照常看终端 B、C 和 `fw job show`：

```
sudo systemd-run --on-active=180 /usr/sbin/iptables -D OUTPUT -p tcp -m owner --uid-owner <跑 worker 的账号> -m conntrack --ctorigdstport 8000 -j DROP   # 先定好 180 秒后撤掉
sudo iptables -I OUTPUT -p tcp -m owner --uid-owner <跑 worker 的账号> -m conntrack --ctorigdstport 8000 -j DROP                                         # 再开始拦
```

- 这条规则按连接原本要去的端口拦，所以 worker 登录时写的是 `127.0.0.1` 还是服务器的局域网地址都拦得住（只按目的地址写的规则拦不住局域网地址：Docker 先把它改成了容器的地址）。已经建立的连接也一样被拦。撤掉的那一条 `-D` 后面的参数要和 `-I` 的完全一样。
- 拦上以后先确认真的拦住了：`sudo -u <跑 worker 的账号> curl -m 5 http://127.0.0.1:8000/api/v1/health` 应该超时。没有超时就撤掉规则，不要往下做。
- worker 的设置文件里 `server` 写的如果是 `http://localhost:8000`，先改成 `http://127.0.0.1:8000`（`fw login` 重新登一次）：`localhost` 可能走 IPv6，这条规则管不到。
- 平台的端口不是 8000（`deploy/.env` 里的 `FW_PORT`）就把两条里的 8000 都换掉。
- `iptables` 的路径用 `command -v iptables` 查。到时间没有自动撤掉的话，手工执行第一条里 `iptables -D …` 那一段；`sudo iptables -S OUTPUT` 能看到规则还在不在。
- 5a 把 180 换成 20，5c 换成 60。
- 这样拦的时候，这个账号在服务器上敲的 `fw` 命令也连不上平台，所以提交任务和 `fw job show` 要在另一台电脑上做。
- 这条规则在 Docker 29 的默认设置下实测过（`127.0.0.1` 和局域网地址都拦得住，别的账号不受影响，撤掉后恢复）；定时撤掉的那一条没有实测过，所以先留意 180 秒后规则是不是真的没了。

**第 4 步断电或强制重启后应该看到：**

- 平台的两个容器自己起来（`docker compose ps`；它们设了 `restart: unless-stopped`，前提是 Docker 服务开机自启），worker 的 systemd 服务也自己起来。worker 起得比平台早的话会先输出「连不上平台……连上后继续领任务」，然后「平台连上了」。
- 断电前在跑的任务回到「排队」，被第 2 次领取，最后「完成」。
- 在服务器上跑 `docker compose exec server fw-server verify`，应该是「问题 0 个」；如果它说要加 `--rehash` 才能解除，就是下面这种情况。
- **如果断电时平台正好在往文件库里写东西**（有人在上传，或者 worker 正在交结果），重启后平台会拒绝一切写入，上传和交结果都报错。这是为了不让数据库引用到没落盘的文件，是设计好的，不是故障：跑一次 `docker compose exec server fw-server verify --rehash`，通过后自动解除（它要把文件库里每个文件读一遍，数据多时要一些时间）。记下有没有遇到、verify 跑了多久。
- 这台机器上有别人的训练或程序在跑时，不要做这一步。

## 第 1 步：正常跑完一次（对照）

1. 终端 A 提交任务，记下编号。
2. 等它跑完。

应该看到：状态「完成」，领取 1 次；终端 B 有「领取任务 N（评估，第 1 次）」；跑完后 GPU 上没有进程，工作目录里没有留下子目录。记下它总共跑了多久，后面每一步都在它跑到一半时动手。

## 第 2 步：`systemctl stop`（正常停掉 worker）

1. 提交一个新任务，等终端 B 出现「领取任务」，再等 1 分钟让推理真的跑起来（`nvidia-smi` 里能看到进程）。
2. GPU 机上：`sudo systemctl stop fw-worker`，记下时间。
3. 马上看终端 C。
4. 终端 A 每 20 秒 `fw job show <编号>` 一次，直到状态变化，记下变化的时间。
5. `sudo systemctl start fw-worker`。

应该看到：

- 停掉后几秒内 GPU 上的推理进程消失（systemd 会把这个服务的全部进程一起停掉）。
- 停掉后 40 到 60 秒租约到期，之后第一次 `fw job show` 就从「运行中」变成「排队」，第 1 次领取的结束方式是「失联（租约过期）」。
- worker 起来后领到同一个任务，「第 2 次」，最后「完成」。
- 结果和第 1 步同一个模型、同一批图的结果一致（指标一样）。

## 第 3 步：`kill -9`（worker 进程突然死掉）

1. 提交一个新任务，等推理跑起来。
2. GPU 机上：`sudo systemctl kill -s KILL --kill-who=main fw-worker`（只杀 worker 主进程，不动它起的推理进程），记下时间。
3. **马上看终端 C：推理进程还在不在。** 这一条自动测试测不到，是这一步最要紧的观察。
4. systemd 会在 10 秒后把 worker 重新起来（`Restart=always`、`RestartSec=10`）。看终端 B：新的 worker 起来后在做什么。
5. 终端 A 看 `fw job show`，直到任务结束。

应该看到：

- 主进程死掉后，systemd 认为服务退出，把这个服务剩下的进程（推理进程）也清掉：先发 SIGTERM，一般几秒内 GPU 上就没有进程了；推理进程不理 SIGTERM 的话，systemd 要等 `TimeoutStopSec`（默认 90 秒）才强杀，worker 也要等到那之后再过 10 秒才重新起来。记下实际等了多久。**如果推理进程还在，记下来**：说明 systemd 的配置不是默认的 `KillMode=control-group`，要在服务文件里补上。
- 新起来的 worker 在旧任务的租约到期之前领不到它（它还显示「运行中」），先「没有任务」；租约到期后（杀掉后 40 到 60 秒）领到，「第 2 次」，最后「完成」。
- 工作目录里第 1 次留下的子目录：记下有没有、多大。留下了不影响结果，但要知道会不会攒起来占盘。

再做一遍不用 systemd 的情况（有人手工在终端里跑 `fw worker` 时会遇到）：`sudo systemctl stop fw-worker` 后在终端里直接 `fw worker`，提交任务，等推理跑起来，另开一个终端 `kill -9 <fw worker 的进程号>`。2026-11-13 之前的 `fw` 在这种情况下推理进程会留在 GPU 上（没有人替它收尾）；现在下一个启动或领到任务的 worker 会把它停掉。它的输出是接在 worker 上的，worker 没了以后它下一次打印东西时会出错，可能就此退出；平时不怎么打印的推理程序则可能一直跑到最后。记下它是不是真的留下了、活了多久、这期间重新起来的 worker 领到同一个任务时两个推理是不是同时占着 GPU、第 2 次是不是因为显存不够而失败。结论会决定要不要让 worker 启动时清理上一次留下的进程。

## 第 4 步：GPU 机断电或强制重启

1. 提交一个新任务，等推理跑起来。
2. 在 GPU 机上 `sudo reboot -f`（不走正常关机流程，接近断电；条件允许的话真的按一次电源键断电）。
3. 终端 A 看 `fw job show`，记下状态什么时候变成「排队」。
4. 机器起来后，确认 `systemctl status fw-worker` 是自己起来的，看终端 B。

应该看到：

- 机器起来之前，有人看 `fw job show` 时任务在租约到期后回到「排队」（2026-11-14 起没人看也会变，见规则 3）。
- 机器起来后 worker 自动领到任务，「第 2 次」，最后「完成」，结果和第 1 步一致。
- 引擎缓存没有坏：第 2 次的日志里要么是「用缓存的引擎」，要么是「缓存里的引擎……不完整……删掉重建」然后重建成功。不应该出现用了半个引擎文件而推理报错。**如果断电正好发生在建引擎的时候，这一条最有价值**：想专门测就找一个这台机器没建过引擎的模型，在日志出现「建引擎」之后断电。
- 工作目录里上一次留下的子目录：记下有没有。

## 第 5 步：拔网线（worker 活着，但连不上平台）

这一步测规则 4：两边都以为自己在跑的时候，谁算数。

怎么断网，按你人在哪里选：

- **人在 GPU 机旁边**（接着显示器和键盘）：直接拔网线，到时间插回。终端 B、C 开在这台机器的本地屏幕上。
- **远程（SSH 连着 GPU 机）**：网卡一关 SSH 就断了，手工敲不了恢复的命令，所以**必须用一条到时间自己恢复的命令**，并且先把要看的东西记到文件里，事后看：

  ```
  sudo systemd-run --unit=smi-log sh -c 'nvidia-smi -l 1 > /tmp/smi.log'   # 留下 GPU 的记录；不挂在 SSH 上，断线了也接着记
  sudo systemd-run --on-active=180 /usr/sbin/ip link set <网卡> up          # 先定好 180 秒后恢复（ip 的路径用 command -v ip 查）
  sudo ip link set <网卡> down                                        # 再断
  ```

  SSH 会卡住或断开，等时间到了重新连上，用 `journalctl -u fw-worker --since "<断网的时间>"` 看这期间 worker 说了什么，用 `/tmp/smi.log` 看 GPU 上的进程是什么时候消失的；看完 `sudo systemctl stop smi-log` 停掉记录。5a 把 180 换成 20，5c 换成 60。
- **不要用这个办法的情况**：平台服务器和 GPU 机是同一台；或者你不确定 `<网卡>` 是哪一块（`ip route get <平台服务器的地址>` 会告诉你走的是哪块网卡）。恢复的那条命令没有先成功就不要断。

5a，短断（20 秒）：

1. 提交一个新任务，等推理跑起来。
2. 断网 20 秒再恢复。
3. 看终端 B 和 `fw job show`。

应该看到：worker 输出「续租或发日志失败，稍后再试」，插回后续上，任务照常「完成」，领取还是 1 次。`fw job log` 里的输出中间不缺行。

5b，长断（超过租约）：

1. 提交一个新任务，等推理跑起来。
2. 断网，记下时间，**保持 3 分钟**。
3. 这期间看终端 B 和终端 C（人在机器旁边时；远程做就事后看记录）。
4. 这期间在终端 A 看 `fw job show`。有第二台 worker 的话，看它是不是领走了这个任务。
5. 3 分钟后插回网线，再看终端 B 和 `fw job show`，直到任务结束。

应该看到：

- 断网后 40 到 60 秒（按 GPU 机自己的时钟），worker 输出「租约到期前没能续上（连不上平台），停下任务，这次领取作废」，**GPU 上的推理进程随即消失**。它不会一直跑到网络恢复。
- 平台这边，租约到期后任务回到「排队」；有第二台 worker 时被它领走，「第 2 次」。
- 插回网线后，第一台 worker 输出「平台连上了」，然后正常领下一个任务。它**不会**把断网前那一次的结果交上去；`fw job show` 里第 1 次领取的结束方式是「失联」，不是「完成」。
- 整个过程中，`nvidia-smi` 里同一个任务的推理进程最多只在一台机器上有。
- 最后任务「完成」，结果和第 1 步一致，评估报告只有一份。

5c，结果交不上（推理跑完的那一刻网络是断的）：

1. 提交一个新任务。估好它快跑完的时间（用第 1 步记下的时长），在跑完前约 30 秒断网。
2. 看终端 B。1 分钟后恢复。

应该看到：worker 输出「交结果没成功……秒后再试」，插回后交上，任务「完成」，领取 1 次。如果断的时间超过了租约，应该看到「这次领取作废」，任务回到队列重新跑一次，最后仍然只有一份结果。

## 第 6 步：取消一个运行中的任务

1. 提交一个新任务，等推理跑起来。
2. 终端 A：`fw job cancel <编号>`，记下时间。
3. 看终端 B、C 和 `fw job show`。

应该看到：最多 20 秒后 worker 输出里有「任务已取消」，GPU 上的进程消失，状态「已取消」，工作目录里没有留下子目录。之后提交的新任务能正常领取和完成。

再测一次「取消时 worker 正好失联」：提交任务，等推理跑起来，`sudo systemctl stop fw-worker`，马上 `fw job cancel <编号>`，60 秒后 `fw job show`。应该是「已取消」，不是回到「排队」；再起 worker，它不会领到这个任务。

## 第 7 步：平台服务器重启（worker 和网络都正常）

1. 提交一个新任务，等推理跑起来。
2. 平台服务器上：`docker compose restart`（在部署目录里），或者重启整台服务器。
3. 看终端 B 和 GPU。

应该看到：

- 服务器在租约到期之前回来的话（40 秒内一定算，40 到 60 秒看运气）：worker 输出几行「续租或发日志失败，稍后再试」，然后续上，任务「完成」，领取 1 次，推理没有中断。
- 服务器过了 60 秒才回来的话：worker 按自己的时钟判定租约到期，停下任务；服务器回来后任务回到队列，重新领取，「第 2 次」，最后「完成」。
- 不管哪种，worker 进程自己不退出（`systemctl status fw-worker` 的启动时间没有变）。

## 第 8 步：连着失联三次

1. 提交一个新任务。
2. 每次终端 B 出现「领取任务」后等 30 秒，就 `sudo systemctl kill -s KILL --kill-who=main fw-worker`。连做三次。
3. `fw job show <编号>`。

应该看到：第三次租约到期后状态是「失败」，原因是「领取了 3 次，每次 worker 都在租约到期前失联（掉线、死机或被停掉）」，三次领取的结束方式都是「失联」。任务不会无限地重新排队。之后提交的新任务能正常跑完。

## 2026-11-13 真机上测出来的结果

在平台和 worker 同一台的试点机上（RTX 3070、TensorRT 10.8，真实模型和 10,751 张图，租约 60 秒）跑了第 1、3、6（只测了推理中取消）、8 步：

| 步骤 | 看到的 | 和预期 |
|---|---|---|
| 1 正常跑完 | 1 次领取，约 5 分钟完成 | 一致 |
| 3 kill -9（systemd） | 推理进程 1 秒内消失，10 秒后 worker 重启，46 秒时任务回到队列，第 2 次领取完成，指标和预测文件的 SHA256 与正常那次相同 | 一致 |
| 3 kill -9（手工跑） | **推理进程留在 GPU 上 259 秒（一直跑到完）**，51 秒时任务被常驻 worker 第 2 次领取，从第 60 秒起两个推理同时占着 GPU 约 200 秒；最后只登记了一份报告，结果正确 | **不一致，已修** |
| 6 推理中取消 | 6.1 秒后停下，GPU 和任务目录都清了 | 一致 |
| 8 连着三次 | 三次都是失联，任务失败，原因是「领取了 3 次，每次 worker 都在租约到期前失联」；随后的新任务一次完成 | 一致 |
| 每次被杀的领取 | 留下一个 `job-<任务编号>-<第几次领取>` 目录，大约 120 MB 不是链接 | **已修** |

修法：worker 启动时和每次领到任务时，停掉这台机器上已经没了的 worker 留下的进程，删掉没有 worker 在用的任务目录（见 `docs/commands.md` 的 `fw worker`）。所以现在第 3 步手工跑的那一遍应该看到：常驻 worker 第 2 次领到任务时打印「停掉了它留下的 N 个进程，删掉了它留下的 1 个任务目录」，`nvidia-smi` 里任何时候只有一个推理进程。

还没有在真机上做的：第 2 步（`systemctl stop`）、第 4 步（断电）、第 5 步（三种断网）、第 6 步里失联期间取消、第 7 步（平台重启）。

## 我预计最可能和预期不一样的三处

（第 1、2 处在 2026-11-13 的真机测试里证实了，已经修掉，见上一节；第 3 处在 2026-11-14 修掉：平台自己定时查租约。）

这三处是读代码时觉得真机上最可能出岔子的地方，自动测试没有覆盖，做的时候多留意：

1. **第 3 步手工跑 worker 时 `kill -9`**：推理进程在自己的进程组里，worker 死了没有人杀它，会留在 GPU 上，直到它跑完或者下一次打印输出时出错退出。用 systemd 常驻时由 systemd 清理，所以正式部署不受影响，但值得确认。
2. **工作目录留下的子目录**（第 3、4 步）：worker 被杀或断电时来不及删，下次启动也不清理。每次留下的是这个任务的图片和权重的摆放（多数是指向缓存的链接，占盘不大），次数多了会攒起来。
3. **规则 3**：只有一台 worker 而且它整台机器没了的时候，任务页没人看就一直显示「运行中」。看一眼就会更正，但不看的话不会有人知道任务停了。
